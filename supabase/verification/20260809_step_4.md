# Step 4 verification — Cloudinary image lifecycle

Date: 2026-08-09 (Asia/Kathmandu)

## Scope

This step hardens the existing Cloudinary integration without changing the locked public or admin layout.

## Implemented

- JPEG and PNG are the only accepted work-image inputs.
- The browser rejects empty files and images larger than the account's 10 MB image limit before upload.
- Every file receives a fresh admin-authorized signed upload request.
- Returned assets must be WebP, use an HTTPS URL from the configured Cloudinary account, include positive dimensions and byte size, and fit the approved 1080p master bounds:
  - landscape: at most 1920 × 1080;
  - portrait: at most 1080 × 1920;
  - square: at most 1080 × 1080.
- Multiple uploads are processed sequentially. If a later file fails, earlier files from that selection are deleted automatically.
- Rejected Cloudinary responses are cleaned up when a public ID was already created.
- Delete requests accept any total number of images by sending authenticated batches of at most 20 IDs.
- Cloudinary `destroy` results are checked explicitly. Both `ok` and `not found` are treated as idempotent success.
- Removing a newly uploaded image deletes it from Cloudinary immediately.
- Cancel and logout clean up images that have been uploaded but not saved.
- A failed database save attempts to remove all newly uploaded images.
- Work deletion now removes the Supabase record first and performs Cloudinary cleanup second, so a Cloudinary failure cannot leave the public database pointing at deleted images.
- The existing dynamic image grid remains unchanged: it displays at least four placeholders and adds one rendered slot for every uploaded image, with no application-level image-count cap.
- Cloudflare Pages Function runtime types were regenerated from `wrangler.jsonc`.
