# Step 5 verification — atomic work CRUD and public synchronization

Date: 2026-08-09

## Scope

- Keep the locked public and admin interfaces unchanged.
- Make work creation and editing atomic across `works` and `work_images`.
- Keep work deletion and its image-row cascade atomic.
- Return the authoritative Cloudinary public IDs from the database for safe
  post-commit asset cleanup.
- Refresh the same Supabase-backed public content after every successful write.

## Implementation

- Added pending migration `20260809200422_atomic_work_crud.sql`.
- Added `public.save_work_with_images(...)` as a `SECURITY INVOKER` function.
  It updates or inserts the work, replaces its ordered image rows, and returns
  the work ID. Any validation, constraint, RLS, or insert failure aborts the
  entire RPC transaction.
- Added `public.delete_work_with_images(bigint)` as a `SECURITY INVOKER`
  function. It captures the work's Cloudinary IDs, deletes the work, relies on
  `ON DELETE CASCADE` for image rows, and returns the captured IDs.
- Revoked default execution from `PUBLIC`, `anon`, `authenticated`, and
  `service_role`, then granted execution only to `authenticated`. Underlying RLS
  still requires an active row in `admin_users` for every mutation.
- Updated the repository to use these RPCs instead of separate table requests.
- Kept public synchronization through `refreshContent()` after each successful
  save or delete.

## Deployment boundary

All Step 5 changes are local only. No migration was applied, no production data
was modified, and no Git commit, push, or Cloudflare deployment was performed.
During the approved deployment step:

1. Apply `20260809200422_atomic_work_crud.sql` through the migration-aware
   Supabase deployment flow.
2. Regenerate `app/rupantar/database.types.ts` from production.
3. Deploy the matching application build.
4. Run authenticated create, edit, failed-edit rollback, multi-image ordering,
   delete/cascade, logout, and public-page refresh smoke tests.
